# Разделение системы на домены и моделирование потоков данных

Архитектура построена на основе **Domain-Driven Design (DDD)** и **Data Mesh** с учетом следующих принципов:
- **Организационной структуры** - каждый домен соответствует бизнес-подразделению
- **Ограниченных контекстов (Bounded Contexts)** - четкие границы ответственности
- **Бизнес-возможностей (Business Capabilities)** - домены группируются по функциям
- **Независимости данных** - каждый домен владеет своими данными
- **Масштабируемости** - возможность добавления новых доменов без изменения существующих

## Домены

### Healthcare - медицинские услуги
Выделен для обеспечения независимого развития мед направления, изоляции чувствительных данных, а также возможности масштабирования клиник без влияния на другие домены.

**Ответственность**:
- Управление пациентами (регистрация, профили)
- Записи на прием к врачам
- Управление расписанием клиник
- Операционные данные клиник
- Результаты приемов (без детальных медицинских данных)

**Данные в домене**:
- Клиенты (ФИО, контакты, базовая информация)
- Записи на прием
- Расписание врачей и клиник
- Финансовые данные о приемах (стоимость, оплата)
- Персонал клиник
- Инвентаризация медицинского оборудования
- Медицинские карты (исключены из аналитики по требованию бизнеса)
- История болезней (исключены из аналитики)
- Результаты диагностических исследований (исключены из аналитики)

---

### Fintech - финансовые услуги
Выделен для удовлетворения требований к изоляции банковских данных, для обеспечения безопасности и аудита, а также для быстрого развития финансовых продуктов и независимого масштабирования финтех-направления.

**Ответственность**:
- Управление счетами клиентов
- Кредитование
- Платежи и транзакции
- Финансовая история клиентов
- Интеграция с платежными системами

**Данные в домене**:
- Счета клиентов
- Кредиты и займы
- Транзакции
- Финансовая история
- Кредитный скоринг
- Платежные данные

---

### AI/ML
Выделен, т.к. имеет специфичный технологический стек (Python, ML-frameworks), а также для обеспечения итеративного процесс разработки моделей, изоляции экспериментов от продакшен-данных и возможности быстрого внедрения новых моделей.

**Ответственность**:
- Разработка и обучение ML-моделей
- Inference (применение моделей)
- Управление фичами (Feature Store)
- Версионирование моделей
- Мониторинг качества моделей
- Результаты анализа (не сами медицинские данные!)

**Данные в домене**:
- ML-модели и их версии
- Фичи для моделей
- Результаты предсказаний (рекомендации, скоринг)
- Метрики качества моделей
- Эксперименты (MLflow)
- Сырые медицинские данные (только получают их для обработки, не хранят)

---

### Corporate - корпоративное управление
Выделен т.к. имеет отдельную сферу ответственность (головного офиса), для обеспечения централизованного управления ресурсами, консолидированной отчетности и независимости от операционных доменов.

**Ответственность**:
- Управление персоналом (HR)
- Инвентаризация
- Финансовая отчетность компании
- Управление офисами и клиниками
- Закупки и снабжение

**Данные в домене**:
- Данные о сотрудниках
- Инвентаризация
- Финансовая отчетность (консолидированная)
- Данные о недвижимости (офисы, клиники)
- Закупки и контракты
- Управленческие метрики

---

### Analytics - аналитика и отчетность
Выделен для обеспечения централизованной точки доступа к аналитике и единой точка управления данными и политиками, а также для изоляции аналитических запросов от операционных систем и оптимизации аналитических запросов.

**Ответственность**:
- Предоставление аналитических витрин данных
- Сквозная аналитика по всем направлениям
- Self-Service Portal для бизнес-пользователей
- Data Catalog - каталог данных
- Data Governance - управление данными

**Данные в домене**:
- Domain Data Products - витрины от каждого домена
- Central DWH - агрегированные метрики
- Метаданные о данных (Data Catalog)
- Политики доступа

---

### Pharma - фармацевтические компании (будущий домен)

**Ответственность** (планируется):
- Управление лекарствами и препаратами
- Рецепты
- Взаимодействие с аптеками
- Информация о наличии лекарств

**Интеграция**:
- События о назначениях из Healthcare → Pharma
- Pharma публикует события о выдаче лекарств → Healthcare, Fintech
- Data Product с данными о продажах лекарств → Analytics

---

### Medical Equipment - производители оборудования (будущий домен)

**Ответственность** (планируется):
- Данные о медицинском оборудовании
- Техническое обслуживание
- Заявки на ремонт
- Обновления ПО оборудования

**Интеграция**:
- Healthcare публикует события об использовании оборудования → Medical Equipment
- Medical Equipment публикует события о необходимости ТО → Corporate, Healthcare
- Data Product с данными о состоянии оборудования → Analytics

## Обоснование разделения на домены

Разделение на домены приносит бизнесу следующие преимущества:

### 1. Ускорение вывода продуктов

**Проблема**:
- Все изменения в одном DWH
- Любое изменение требует согласования со всеми командами
- Time-to-market: 2-3 месяца

**Решение через домены**:
- Каждый домен разрабатывается независимо
- Изменения в Healthcare не влияют на Fintech
- Каждая команда может делать deploy самостоятельно

**Результат**:
- Сокращение Time-to-market
- Быстрее реакция на конкурентов

### 2. Снижение зависимости от DWH

**Проблема**:
- Вся бизнес-логика в DWH (MS SQL Server 2008)
- DWH - единая точка отказа
- Любое изменение требует изменения DWH
- Перегрузка IT-отдела (все идут к DBA)

**Решение через домены**:
- Каждый домен имеет свою БД
- Бизнес-логика в микросервисах, а не в БД
- DWH становится опциональным (только для сквозной аналитики)

**Результат**:
- Нет единой точки отказа
- IT-отдел не перегружен
- Каждый домен оптимизирован под свои нагрузки
- Можно использовать разные БД (PostgreSQL, MongoDB, etc.)

### 3. Независимое развитие направлений

**Проблема**:
- Одна команда поддерживает всё
- Нельзя нанимать специализированных специалистов
- Конфликты между командами из-за общих ресурсов

**Решение через домены**:
- **Healthcare команда**: врачи + Java разработчики
- **Fintech команда**: финансисты + Golang разработчики + security
- **AI/ML команда**: data scientists + ML engineers (Python)
- **Corporate команда**: HR + ERP специалисты

**Результат**:
- Автономные команды
- Специализированные навыки
- Параллельная разработка
- Независимые циклы релизов

### 4. Масштабирование для новых бизнесов

**Проблема раньше**:
- Добавление партнера = изменение DWH, ESB, всех систем
- Онбординг: 2-3 месяца
- Высокий порог входа

**Решение через домены**:
- Стандартизированный подход к онбордингу
- Новый партнер = новый домен
- Шаблоны: Domain Service Template, Data Product Template
- API Gateway автоматически регистрирует новые сервисы

**Результат**:
- Checklist для новых партнеров
- Plug-and-play интеграция
- Автоматическое появление в аналитике
-

### 5. Compliance и безопасность

**Проблема раньше**:
- Медицинские карты в одной БД с финансами
- Сложно обеспечить изоляцию
- Нет четкого аудита доступа

**Решение через домены**:
- **Healthcare**: изоляция медицинских данных (только персонал клиник)
- **Fintech**: изоляция финансовых данных (требования ЦБ РФ)
- **AI/ML**: НЕ хранит медицинские данные, только обрабатывает
- Каждый домен имеет свои политики доступа

**Результат**:
- Соответствие требованиям регуляторов
- Audit trail по каждому домену
- Row-level security в каждом домене
- Прохождение сертификаций

### 6. Оптимизация затрат

**Проблема раньше**:
- Все данные в одном дорогом DWH
- Нельзя оптимизировать стоимость хранения
- Переплата за неиспользуемые ресурсы

**Решение через домены**:
- Каждый домен выбирает оптимальное хранилище
- Холодные данные → S3 Glacier
- Аналитика → Snowflake (pay-per-query)
- Операционные данные → PostgreSQL (дешевле)

**Результат**:
- Экономия на инфраструктуре
- Прозрачность затрат
- Точечная оптимизация под нагрузку
