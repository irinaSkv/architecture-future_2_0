# Обоснование конфигурации

Конфигурация упрощенная, для варианта "на попробовать" на начальном этапе перехода.

## Почему такая сеть (Network/Subnet/NAT)

- **Одна сеть VPC**: проще стартовать, меньше операционных рисков.
- **Public subnet**: содержит только bastion (единственная VM с публичным IP).
- **Private subnet**: содержит основные VM (data-platform и portal) без публичных IP.
- **NAT gateway + route table**: приватные VM получают исходящий доступ в интернет (обновления/репозитории), но входящих соединений извне нет.
- **Security Groups**:
    - bastion: разрешён SSH только из `ssh_allowed_cidrs`;
    - private: SSH только из public-subnet (через bastion), HTTP — только из public-subnet (если делать проксирование/туннель).

Такой подход снижает риски, особенно для медицинских и финансовых данных.

## Почему такие размеры VM и дисков

Размеры выбраны как “разумный старт”, чтобы не переплачивать, но иметь запас:
- **Bastion (2 vCPU, 2 GB RAM)** — достаточно для SSH, администрирования и лёгких утилит.
- **Data-platform (4 vCPU, 8 GB RAM)** — стартовый размер для задач загрузки/подготовки данных и сервисов платформы.
- **Portal (2 vCPU, 4 GB RAM)** — достаточно для веб-приложения и фоновых задач на старте.

Диски:
- **Отдельный диск для data-platform (200 GB)** — под данные/логи/временные файлы.
- **Отдельный диск для portal (50 GB)** — под логи/артефакты/кэш.
  Тип дисков `network-ssd` выбран как баланс производительности и простоты.

## Что управляется Terraform, а что вручную

**Terraform (IaaS):**
- сеть, подсети, NAT, маршрутная таблица,
- security groups,
- VM, boot disks, дополнительные disks,
- связи ресурсов (зависимости).

**Вручную (после создания инфраструктуры):**
- установка и настройка приложений (портал/ETL/хранилища),
- настройка секретов (пароли, ключи, токены),
- настройка доменных имён и TLS-сертификатов,
- CI/CD, мониторинг, резервное копирование на уровне приложений.

## Почему Terraform?

- Multi-cloud: Если в будущем мигрируем на AWS/Azure - 70% кода переиспользуется
- Ecosystem: 3000+ providers (Yandex, Kubernetes, Datadog, PagerDuty)
- Community: Огромное community, много примеров
- Declarative: HCL легко читается и понимается (vs Pulumi)
- Industry standard: Terraform - де-факто стандарт для IaC

## Преимущества IaC подхода

### 1. Воспроизводимость:
- Нет "configuration drift" (ручные изменения)
- Идентичные dev/staging/prod (кроме sizing параметров)
- Disaster Recovery: terraform apply восстанавливает инфраструктуру за 20-25 минут

### 2. Версионирование:
- История изменений инфраструктуры (кто, когда, что)
- Code review для infrastructure changes (через PR)
- Rollback к предыдущей версии за секунды

### 3. Documentation as Code:
- Terraform файлы = актуальная документация инфраструктуры
- Комментарии в коде объясняют решения
- terraform show - текущее состояние инфраструктуры

### 4. Testing:
- Preview changes перед применением
- Автоматизация тестов в CI/CD

### 5. Collaboration:
- Team работает над одной конфигурацией (Git)
- Locking mechanism - предотвращает concurrent changes
